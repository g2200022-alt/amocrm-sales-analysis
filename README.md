# Анализ работы отдела продаж: amoCRM + телефония

Тестовое задание для вакансии AI-оператор/AI-агент (CityCar).

## 1. Архитектура решения

Запрос руководителя: «Проанализируй работу отдела продаж за последние 30 дней».
Источники: amoCRM (сделки, задачи) и телефония (записи звонков).

Я бы разбил систему на четырёх агентов, каждый делает свою часть:

**Агент-координатор.** Принимает запрос, понимает, что от него хотят, и раздаёт задачи остальным. Когда данные собраны — собирает итоговый отчёт.

**Агент данных.** Забирает информацию из amoCRM через REST API v4: сделки (суммы, этапы, даты, ответственные), задачи (сроки, статусы), контакты. Отдельно подключается к телефонии — у большинства провайдеров тоже есть API, через который выгружаются звонки за период: кто звонил, кому, длительность, ссылка на запись.

**Агент расшифровки.** Скачивает записи звонков по ссылкам и прогоняет через распознавание речи (Whisper или облачный SpeechKit). Дальше текст разговора анализируется через LLM: был ли звонок результативным, о чём договорились, какие были возражения. Так из «просто записей» получается структура, которую можно считать.

**Агент-аналитик.** Все цифры считает обычный код, а не нейросеть: конверсия по этапам, зависшие сделки, сделки без задач и с просроченными задачами, пропущенные звонки, результативность звонков. LLM только формулирует выводы и пишет текст отчёта. Это принципиально: если считать цифры нейросетью, она однажды посчитает их неправильно, и никто не заметит.

**Хранение:** сырые данные и расшифровки — в PostgreSQL, отчёты — в базе плюс отправка руководителю в Telegram или на почту. Отчёты сохраняются, чтобы можно было вернуться и сравнить с прошлыми периодами.

Схема одной строкой: руководитель → координатор → (amoCRM API + телефония API + расшифровка звонков) → аналитик → отчёт.

## 2. Что делает система, а что человек

Система сама: собирает данные, расшифровывает звонки, считает метрики, пишет черновик отчёта, находит проблемные места (зависшие сделки, просроченные задачи, пропущенные звонки).

Человеку остаётся: читать выводы и принимать решения — кого из менеджеров подтянуть, где узкое место воронки, что менять в скриптах. Оценку людей («Иванов работает плохо») система не даёт — только факты, выводы делает руководитель.

Три главных риска:

1. **Галлюцинации LLM.** Все числа считает код, LLM только объясняет уже посчитанное. Каждая цифра в отчёте имеет источник, который можно проверить.
2. **Персональные данные в записях звонков.** В разговорах называют имена, телефоны, суммы. Расшифровки — с ограниченным доступом; при жёстких требованиях к безопасности — локальное распознавание вместо облака.
3. **Ошибки распознавания и трактовки.** Speech-to-text ошибается на именах и цифрах, LLM может неверно понять итог звонка. Поэтому выводы показываются как «в N звонках из M зафиксировано то-то», а не как истина в последней инстанции.

## 3. Код: сделки без задач или с просроченными задачами (Python)

```python
import os
import time
import requests

SUBDOMAIN = os.getenv("AMO_SUBDOMAIN")   # например, "citycar"
TOKEN = os.getenv("AMO_TOKEN")           # long-lived access token
BASE = f"https://{SUBDOMAIN}.amocrm.ru/api/v4"
HEADERS = {"Authorization": f"Bearer {TOKEN}"}

def get(url, params=None):
    """GET с учётом лимитов amoCRM (у бесплатных тарифов ~2 rps)."""
    r = requests.get(url, headers=HEADERS, params=params, timeout=15)
    r.raise_for_status()
    time.sleep(1)
    return r.json().get("_embedded", {}).get("items", [])

def leads_with_task_issues():
    # 1. Все сделки постранично
    leads, page = [], 1
    while True:
        chunk = get(f"{BASE}/leads", {"page": page, "limit": 250})
        if not chunk:
            break
        leads += chunk
        page += 1

    # 2. Задачи, сгруппированные по сделкам
    tasks_by_lead = {}
    for t in get(f"{BASE}/tasks", {"limit": 250}):
        tasks_by_lead.setdefault(t["entity_id"], []).append(t)

    now = time.time()
    no_tasks, overdue = [], []
    for lead in leads:
        tasks = tasks_by_lead.get(lead["id"], [])
        if not tasks:
            no_tasks.append(lead["id"])
        elif any(t["complete_till"] and t["complete_till"] < now
                 and not t["is_completed"] for t in tasks):
            overdue.append(lead["id"])
    return {"no_tasks": no_tasks, "overdue": overdue}

if __name__ == "__main__":
    r = leads_with_task_issues()
    print("Сделок без задач:", len(r["no_tasks"]))
    print("Сделок с просроченными задачами:", len(r["overdue"]))
```

## 4. Реальный AI-проект

AI-секретарь для бизнеса — сервис, который отвечает клиентам вместо живого администратора.

Задача: студия флоатинга и СПА теряла заявки — клиенты писали в Telegram после рабочего дня, наутро часть уже уходила к конкурентам. Нужен был «секретарь», который отвечает сразу, в любое время, по базе знаний студии.

Что сделал: Telegram-бот, который принимает входящие сообщения, отвечает на вопросы по ценам, услугам и правилам (база знаний собирается из короткой анкеты владельца), записывает клиента, а готовую заявку со всеми контактами сам отправляет в рабочий чат и в Google-таблицу. Если вопрос вне базы — честно говорит «передам администратору» и фиксирует вопрос, а не выдумывает ответ. Цены в ответах — только дословно из базы, это жёсткое правило.

На чём сделано: Python, Telegram Bot API, LLM (YandexGPT по API), сервер на Ubuntu (systemd, nginx), Google Sheets API. Работает в проде круглосуточно, переживает перезагрузки сервера.

Результат: студия перестала терять ночные заявки, заявка доходит до администратора в течение минуты после диалога, без участия человека. Сейчас оформляю это в продукт (сайт аисекретарь.рф, канал в Дзене о применении ИИ в малом бизнесе), чтобы подключать других клиентов по той же схеме.

## 5. Чему научился самостоятельно за последние полгода

1. Собирать LLM-агентов на OpenClaw: работа агента в живом контуре — память, инструменты, ограничения, чтобы он не выдумывал, а работал по базе знаний. Применил в AI-секретаре — он работает в проде.
2. Администрировать Linux-сервер: Ubuntu, systemd, nginx, HTTPS (Let's Encrypt), PostgreSQL. Все сервисы живут на моих VDS и выдерживают перезагрузки.
3. Поднимать интеграции по чужой документации: Telegram Bot API, Google Sheets, REST API (сейчас в тестовом задании — amoCRM). Читаю доки и быстро делаю рабочую связку.
4. Забирать данные из рекламных кабинетов через API: Яндекс.Директ и Метрика — скрипт по расписанию сам тянет статистику по кампаниям, руками в кабинеты заходить не нужно.
5. Работать с Google-таблицами через API: заявки из бота пишутся в таблицу заказов автоматически — настроил авторизацию, чтение и запись строк.
6. Генерировать изображения нейросетями: Midjourney, Leonardo — обложки для статей и материалы для сайта, раньше это делал дизайнер.
7. Автоматизировать рутину скриптами: отчёты, перенос данных, автопостинг статей в Дзен по расписанию. Всё, что повторяется больше двух раз, отдаю скрипту.
8. Настраивать голосовые интерфейсы: распознавание речи и озвучка — общаюсь со своим ассистентом голосом и встраиваю это в проекты.

## 6. Улучшение, предложенное и доведённое до результата

Заметил проблему и узкое место: в студии все заявки шли в общую группу администратору и менеджеру. Вечером, в выходные и в часы большой загруженности отвечать было некому, часть клиентов терялась, не дожидалась, уходила. Предложил владельцу: вместо ручной переписки внедрить AI-бота, который сам отвечает клиентам по базе знаний и оформляет заявку в таблицу и рабочий чат.

Довёл предложение до результата сам, целиком. Собрал систему из семи файлов-модулей: bot.py (переписка в Telegram), bridge.py (создание настроек клиента из анкеты), test-dialog (проверка бота перед запуском), finalize_booking.py (сборка готовой заявки), onboarding.json (настройки клиента), база знаний (услуги, цены, правила) и клиентские данные. Подключил к системе LLM-модель YandexGPT по API — она ведёт разговор с клиентом по нашей базе знаний. Развернул всё на сервере, провёл живые тесты, исправлял ошибки, пока не добился стабильной работы.

Через неделю всё заработало само: клиент пишет ночью — к утру администратор получает готовую карточку записи, без единого ручного действия. Сотрудники студии ничего в своей работе не меняли — заявки просто прилетают в один чат.
